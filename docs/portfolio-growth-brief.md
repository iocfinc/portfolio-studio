# Portfolio Growth Brief

Date: 2026-06-21

## Decision Frame

Treat the website as a product for proving AI engineering, field engineering,
digital transformation, and product judgment. The site should not merely list
old projects. It should route readers to proof that Ira can discover, explain,
architect, evaluate, and ship AI systems.

## North Star

Observation as craft, evidence as product.

## Proposed Sitemap

- `/`: proof router for current positioning, selected work, latest writing,
  event/gallery signal, and consulting path.
- `/work`: case studies with problem, architecture, tradeoffs, proof, and
  field narrative.
- `/playbooks`: reusable field-engineering artifacts such as AI readiness
  scorecards, discovery workshop templates, RAG evaluation checklists, and demo

- Weeks 1-4: credibility cleanup, stale-link audit, positioning spine, homepage
  proof routing.
- Weeks 2-8: first case study, first playbook, first demo proof surface.
- Weeks 1-12: weekly notes, monthly essays, quarterly flagship essay.
- Weeks 3-10: Codex meetup gallery, reusable gallery model, next event post.

## Release Strategy

- Release 0: credibility reset. Remove false promises, retired demos, dead
  links, stale claims, old contact behavior, and outdated Udacity/Heroku
  surfaces.
- Release 1: AI proof kit. Ship one flagship AI systems case study, one
  playbook, one demo page, one architecture diagram, and one public-safe field
  note.
- Release 2: field engineering surface. Ship an AI discovery workshop, AI
  readiness scorecard, RAG/eval checklist, stakeholder narrative, and
  demo-to-POC handoff template.
- Release 3: public cadence engine. Ship monthly flagship writing, weekly notes,
  event galleries, social derivatives, and quarterly recap.

## Foreground Versus Background Contract

Foreground work is for CEO/chief-architect decisions:

- approve positioning, sitemap, services stance, and tone
- approve public-safe boundaries for workplace-adjacent writing
- pick flagship proof pieces and reject weak narratives
- review visual direction before broad implementation
- decide when a draft becomes public versus private

Background work is for agent-owned execution:

- audit links, routes, stale claims, screenshots, and mobile states
- draft PRD/ADR/BDD/WTF packets from approved strategy
- generate page skeletons, content calendars, and Linear seeds
- run route smoke, link checks, visual checks, and build commands
- loop on failures until blocked by an explicit decision boundary

Agents should not ask Ira for small execution details that can be inferred from
the approved packet, repo conventions, tests, or existing design system. They
should ask only when the next step changes public positioning, confidentiality
boundaries, service claims, or irreversible publishing decisions.
